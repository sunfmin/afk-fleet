## description (frontmatter)

Run an unattended, standing **fleet** that works a GitHub-issue backlog on its own. Use when the
user wants to autonomously / AFK implement a repo's ready issues, orchestrate a fleet of
agents/workers against GitHub issues (e.g. with orca), "launch workers to do the issues", or keep
picking up and merging ready issues until stopped. A coordinator loop dispatches
worktree-isolated Claude Code workers per ready issue, gates each on CI + optional independent
adversarial verification, auto-merges green PRs to main, and retries-then-escalates failures.
Reads per-repo config and requires an explicit push+auto-merge authorization before running;
supports `--plan` dry-run. NOT for decomposing a PRD/epic into issues, implementing a single
named issue by hand, or reviewing a PR.

## should_fire

1. `用 orca 编排启动 worker 无人值守做这个仓库的 github issues`
2. `launch a fleet of agents to autonomously work through our ready-for-agent issues and merge them`
3. `start the afk fleet on this repo` / `/afk-fleet`
4. `帮我无人值守地把 backlog 里 ready 的 issue 都实现了，自动开 PR 合并`
5. `keep picking up ready issues and implementing them with isolated workers until I stop it`

## decoys (must NOT fire)

1. `把这个 PRD #1 拆成一批可执行的子 issue`  (decomposition — not this skill)
2. `帮我实现 issue #42`  (single issue, by hand — not a fleet)
3. `review the changes on my branch` / `review this PR`  (code review)
4. `create a github issue for this bug`  (issue filing / qa)
5. `run the tests and fix the failures`  (generic dev, no fleet)

## examples

- `/afk-fleet` in a repo whose PRD is already decomposed → reads `docs/agents/afk-fleet.md`,
  shows the dispatch plan, confirms push+auto-merge authorization, starts the standing loop.
- `启动 afk fleet，把 ready-for-agent 的 issue 都跑了` → same.
- `/afk-fleet --plan` → dry-run: prints frontier selection + dispatch plan, spawns nothing.

## needs

- `gh` CLI — issues, PRs, labels, native dependencies API, merge.
- `git` worktrees.
- `orca` / `orca-cli` skill — spawn a real Claude Code worker in a worktree; read/wait/send terminal.
- `orchestration` skill (optional) — dispatch + worker_done/escalation waits for the coordinator.
- `ScheduleWakeup` (harness) — idle-poll cadence of the standing loop.
- `python3` — `scripts/afk.py` (the deterministic tool) over `scripts/afk_decide.py` (pure,
  fixture-tested decision core: frontier + claim/lease/pace/retry verdicts). Powers `--plan`, the live
  loop, and cooperating multi-fleet.
- Per-repo config: `docs/agents/afk-fleet.md` front-matter block (schema in `references/config-template.md`).

## functional_test

**Task:** run the pure-core unit tests, and run the frontier selector over the fixture to check it
dispatches exactly one.

```bash
python3 scripts/test_afk_decide.py                                      # pure-core suite (7 tests)
python3 scripts/afk.py frontier --fixture references/fixture.issues.json
```

Fixture (`references/fixture.issues.json`):
- `#101` open · `ready-for-agent` · unclaimed · no PR · 0 open blockers → **dispatch**
- `#102` open · `ready-for-agent` · 1 open blocker                       → excluded (blocked)
- `#103` open · `epic`                                                   → excluded (epic / not ready)
- `#104` open · `ready-for-agent` · `claimed` (afk-claim ref)            → excluded (claimed)
- `#105` open · `ready-for-agent` · `has_open_pr`                        → excluded (open linked PR)

**Success condition:** the suite prints `7 passed`; the frontier JSON has `.dispatch == [101]` (the
four others land in `.excluded` with the right reasons). Exit 0. Side-effect-free — no gh, no worktree,
no push.
